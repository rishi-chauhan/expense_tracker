1. Goals & Non-Goals

V2 keeps the app local-first and single-user, but makes it safe and operable as a always-on service on a Raspberry Pi on a home LAN.

Goals

  • Deploy safely on a Raspberry Pi behind a reverse proxy with authentication
  • Protect financial data from other devices on the LAN
  • Add production ops: systemd, backups, health checks, env config
  • Close high-value product gaps: categories, statement management, export
  • Improve maintainability (shared API client, CI, doc fixes) without a rewrite

Non-Goals (out of scope for V2)

  • Cloud hosting, SaaS signup, or multi-tenant accounts
  • Mobile native apps (responsive web on LAN is enough)
  • Replacing SQLite with Postgres/MySQL
  • Full TypeScript rewrite in one shot (gradual typing only, if at all)
  • Internet exposure without a carefully reviewed threat model
Constraint: Prefer reverse-proxy auth (Caddy/nginx basic auth) over building a full in-app auth system. In-app login can come later if multi-user is needed.

2. Overview & Current State

Paisa Kidhar Gaya?! is a full-stack local-first expense analyzer built with Bun (backend), React 19 (frontend), and SQLite (storage). Users upload Indian credit card CSV statements; the backend parses and deduplicates transactions; the frontend provides Chart.js dashboards and an optional Ollama AI chat assistant.

3. Security Hardening

The app is designed for single-user localhost use. For Raspberry Pi deployment on a home network, security hardening is the highest priority.

V2 Security Tasks

PriorityTaskDetails
Critical Reverse proxy with authentication Put Caddy or nginx in front with HTTP basic auth. Prefer this over building in-app auth for V2.
Critical Bind app to localhost only Add HOST env support to Bun.serve({ hostname }). Production default: 127.0.0.1.
High HTTPS via reverse proxy Caddy TLS for a real domain, or a self-signed / local CA cert for LAN-only use.
High Firewall rules Allow only LAN (e.g. ufw allow from 192.168.0.0/16 to any port 443). Do not expose the Bun port publicly.
High Server-side upload limits + validation Reject files over MAX_UPLOAD_SIZE (default 5 MB). Validate filename ends with .csv and content looks like CSV.
Medium Security headers Set CSP, X-Frame-Options, X-Content-Type-Options, Referrer-Policy on the proxy or Bun responses.
Medium Static path sanitization Resolve path under dist/ and reject anything that escapes that directory.
Medium Harden AI SQL sandbox Open a second SQLite connection with readonly: true; block sqlite_master / attached DBs; stop returning raw SQL in client errors.
Medium Lock down Ollama Bind Ollama to 127.0.0.1 only on the Pi so the model API is not LAN-open.
Low Encryption at rest Prefer LUKS / encrypted SSD partition over SQLCipher unless there is a strong need.

4. Raspberry Pi Deployment & Operations

Production start exists (bun run build + bun run start), but the repo has no Docker, systemd, nginx/Caddy, or backup scripts. V2 should add a deploy/ directory with everything needed to run on a Pi.

What Exists Today

  • bun run build → Vite builds to dist/
  • bun run start → NODE_ENV=production bun run src/server/index.js
  • SQLite DB at data/expenses.db (gitignored, created at runtime)
  • .env / .env.local gitignored

What V2 Should Add

  • deploy/expense-tracker.service — systemd unit
  • deploy/Caddyfile — reverse proxy + basic auth + headers
  • deploy/backup.sh — nightly SQLite .backup + rotation
  • deploy/install.sh — idempotent Pi setup helper
  • deploy/README.md — step-by-step guide
  • .env.example — documented config knobs
  • GET /api/health — liveness for monitoring / systemd
  • Graceful shutdown on SIGTERM / SIGINT
  • Configurable HOST, DB_PATH, MAX_UPLOAD_SIZE

systemd Service Unit

Auto-start on boot and restart on crash. Prefer bun run start so scripts stay the single source of truth:

# deploy/expense-tracker.service
[Unit]
Description=Paisa Kidhar Gaya Expense Tracker
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=expense
Group=expense
WorkingDirectory=/home/expense/expense_tracker
Environment=NODE_ENV=production
Environment=PORT=3000
Environment=HOST=127.0.0.1
EnvironmentFile=-/home/expense/expense_tracker/.env
ExecStart=/home/expense/.bun/bin/bun run start
Restart=on-failure
RestartSec=5
# Soft hardening
NoNewPrivileges=true
PrivateTmp=true

[Install]
WantedBy=multi-user.target

Database Backups

SQLite on an SD card is a wear and corruption risk. V2 should include:

  • Nightly cron: sqlite3 "$DB_PATH" ".backup '$BACKUP_DIR/expenses-$(date +%F).db'"
  • Store backups on an external SSD (not the boot SD card)
  • Enable WAL mode at startup: PRAGMA journal_mode=WAL
  • Rotate backups (keep last 30 days)
  • Document restore steps in deploy/README.md

Pi Setup Steps (to document)

  1. Install Raspberry Pi OS 64-bit (Pi 4/5 recommended)
  2. Install Bun for linux-arm64
  3. Create dedicated expense system user
  4. Clone repo (or rsync a pre-built tree from a desktop — preferred for weak Pis)
  5. bun install --production (or full install then bun run build)
  6. Copy .env.example → .env, set HOST=127.0.0.1
  7. Install systemd unit, enable and start the service
  8. Install Caddy, apply Caddyfile, open only proxy ports in ufw
  9. Mount external SSD for data/ and backups; point DB_PATH at it
  10. Schedule backup.sh via cron or a systemd timer
  11. (Optional) Install Ollama, pull qwen2.5:1.5b, bind Ollama to localhost
Tip: Building Vite on a low-RAM Pi is slow and can OOM. Prefer building on a laptop (bun run build) and syncing dist/ + source to the Pi, then running only the production Bun server there.

5. Code Architecture Improvements

Not blocking for first Pi deploy, but needed before larger feature work.

Centralize API Client

Fetch calls live in App.jsx and AskAI.jsx with no shared helper, no reliable res.ok handling, and inconsistent base URLs (API_BASE vs hardcoded /api/...).

Create src/client/utils/api.js:

const API_BASE = '/api';

async function api(path, options = {}) {
  const res = await fetch(`${API_BASE}${path}`, options);
  let data;
  try {
    data = await res.json();
  } catch {
    throw new Error(res.statusText || 'Invalid JSON response');
  }
  if (!res.ok || data.success === false) {
    const err = new Error(data.error || res.statusText);
    err.status = res.status;
    err.data = data; // preserve needsCardInfo / isDuplicate payloads
    throw err;
  }
  return data;
}

export const getTransactions = (cardId) =>
  api(`/transactions${cardId ? `?cardId=${cardId}` : ''}`);
export const getCards = () => api('/cards');
export const getStatements = () => api('/statements');
export const uploadCSV = (formData) =>
  api('/upload', { method: 'POST', body: formData });
export const deleteStatement = (id) =>
  api(`/statements/${id}`, { method: 'DELETE' });
export const chatHealth = () => api('/chat/health');
export const chat = (question) =>
  api('/chat', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ question }),
  });
export const health = () => api('/health');
Upload flow is special: needsCardInfo and duplicates are valid non-success outcomes. The client helper should expose err.data so useUpload can branch without treating every non-2xx as a hard failure.

Split App.jsx

App.jsx currently owns global state, routing, upload flow, PascalCase transformation, and header chrome. Extract hooks:

useTransactions()

Fetch transactions + cards on mount; expose data, loading, error, and refetch().

useUpload()

Handle upload, duplicates, needsCardInfo / CardInfoModal, and notifications.

useStatements()

List and delete statements for the new management UI.

Category System Design (Proposed)

Prefer one category per transaction for V2 (simpler UI and analytics). Keep rules as a separate table for auto-tagging. 

-- V2 category tables (proposed)
CREATE TABLE categories (
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL UNIQUE,   -- "Groceries", "Dining", ...
  color TEXT,                  -- chart color
  icon TEXT,                   -- optional icon key
  created_at TEXT NOT NULL
);

CREATE TABLE category_rules (
  id INTEGER PRIMARY KEY,
  category_id INTEGER NOT NULL REFERENCES categories(id) ON DELETE CASCADE,
  pattern TEXT NOT NULL,       -- case-insensitive keyword or simple glob
  priority INTEGER DEFAULT 0,
  UNIQUE(pattern)
);

8. Raspberry Pi Performance Notes

ConcernSeverityRecommendation
Ollama RAM Medium qwen2.5:1.5b ~1–2 GB. Fine on Pi 4/5 with 4+ GB. Keep AI optional and off by default on small boards.
Building on-device Medium Vite builds can OOM on 1–2 GB machines. Build elsewhere and sync dist/.
Large CSV uploads Medium Full-file file.text(). Add size limits first; stream later if needed.
SQLite on SD card Medium Use external SSD for DB_PATH + backups. Enable WAL.
Bun on ARM Low Official linux-arm64 builds target modern 64-bit OS (Pi 4/5). Document supported platforms.
Single Bun process + SQLite Good Right fit for a home Pi — no Redis/Postgres required.
Charts on the client Good Pi serves JSON + static assets; browser does Chart.js work.

10. Recommended Roadmap

Phase 1 — Security & Deployment (ship first)

Safe to leave running on a Pi on the home LAN.

  • HOST binding + production default 127.0.0.1
  • deploy/ systemd + Caddyfile + backup.sh + install notes
  • Upload size limit + basic CSV validation
  • GET /api/health + graceful shutdown
  • .env.example, WAL mode, path sanitization for static files
  • Firewall + Ollama localhost binding documented

Phase 2 — Quality & Maintainability

Safer iteration without regressions.

  • GitHub Actions CI + test:all script
  • Shared api.js client; extract upload/transactions hooks
  • CardInfoModal tests; fix README / TESTING.md / coverage dep
  • User-visible error when initial fetch fails

Phase 3 — Product Features

Make it a better personal finance tool.

  • Statement management UI (wire existing APIs)
  • Categories + rules + migration
  • CSV export; custom date range on home dashboard
  • Budgets / recurring detection (after categories)

Phase 4 — Polish (optional)

Nice-to-haves once the above is stable.

  • Playwright smoke tests; mobile table UX
  • Stream CSV parsing; stronger AI sandbox
  • Disk encryption; gradual TypeScript; multi-user only if needed

12. Success Criteria

V2 Phase 1 is done when all of the following are true:

  • App binds to localhost; only Caddy/nginx is reachable on the LAN
  • Basic auth (or equivalent) required before any financial data is visible
  • Service starts on boot via systemd and survives reboot
  • Nightly DB backup exists and restore steps are documented
  • /api/health returns OK when DB is readable
  • Oversized / non-CSV uploads are rejected server-side
  • Deploy steps are written in deploy/README.md and verified on a Pi (or Pi-like ARM host)

V2 overall (through Phase 3) is done when, in addition:

  • CI runs lint + both test runners on every PR
  • Users can list/delete statements from the UI
  • Users can categorize spending (manual + simple rules) and export CSV
